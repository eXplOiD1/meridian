# ADR 0014: Host-Agent für Shell-Jobs unter systemd (S11)

Status: umgesetzt; gegen echtes systemd noch nicht abgenommen (siehe unten)

Setzt ADR 0004 E3/§5.6 um. Shell-Jobs laufen nie im Meridian-Container und nie als Meridian-Benutzer.

## Entscheidungen

1. **Zwei Prozesse:** Der Shell-Worker (Benutzer `meridian`, hat Schlüssel und Datenbank) startet nichts selbst. Er verbindet sich mit dem Socket `/run/meridian-shell/<profil>.sock` (`meridian-shell.socket`, `Accept=yes`, Modus 0600). systemd startet je Verbindung `meridian-shell@.service` mit `bin/meridian-shell-agent` als **`meridian-run`**: kein Zugriff auf `/etc/meridian`, `/var/lib/meridian`, `/run/meridian-docker`, `NoNewPrivileges`, `ProtectSystem=strict`, `MemoryMax=1G`, `TasksMax=256`, `RuntimeMaxSec=86400`, leere Capability-Menge.
2. **Protokoll** (`Meridian\Runner\Shell\Agent\Frames`): Rahmen `[Typ:1][Länge:4][Daten]`, höchstens 1 MiB; Worker → Agent `S` (Auftrag, JSON), `I` (Skript), `T`/`K` (SIGTERM/SIGKILL an die Gruppe); Agent → Worker `P` (Gruppe, Nonce), `O`/`E`, `X` (Ende mit Exit-Code oder festem Fehlercode). Unerlaubter Typ oder Länge über dem Limit sind ein Protokollfehler **vor** dem Lesen der Daten.
3. **Der Agent prüft alles erneut** (`AgentRequest`): Version, Interpreter aus dem Enum (`sh`/`bash`, nie ein Pfad), Umgebung nach E12 (Namen, Werte, höchstens 50 Variablen, 32 KiB), Nonce, Zeitzone aus der tz-Liste, Skriptgröße (höchstens 256 KiB, UTF-8, kein NUL), genaue Feldmenge. Jede Abweichung: Exit 1, **nichts gestartet**, kein Arbeitsverzeichnis, ein fester Text im Journal (nie Skript oder Werte).
4. **Ausführung** über `LocalProcessExecutor`: eigene Prozessgruppe (`setsid`), Umgebung exakt `PATH`, `LANG`, `HOME`, `TZ`, `MERIDIAN_JOB_ID/RUN_ID/TRIGGER` plus Job-Variablen (nichts vom Agenten geerbt), Arbeitsverzeichnis je Lauf neu im privaten `/tmp`. `HostIsolation` verweigert bei jedem Start root, Container und lesbaren Schlüssel/Datenbankpfad (Antwort `X` mit Fehlercode `isolation`, vom Worker auf einen festen Text abgebildet).
4a. **Verbindungsende = Ende des Laufs:** Schließt der Worker die Verbindung (Abbruch, Zeitlimit, Absturz) oder verletzt er das Protokoll, beendet der Agent die ganze Prozessgruppe (SIGKILL) und endet; systemd räumt die cgroup ab. Ende des Stroms ohne `X` ist im Worker ein Fehler (`HOST_LOST`), nie ein stiller Erfolg; eine fremde Nonce in `P` ein Protokollfehler.
5. **Konfiguration:** `MERIDIAN_SHELL_HOST_SOCKETS=default=/run/meridian-shell/default.sock[,profil=pfad…]` (`HostSockets`: Profilname wie in der Freigabe, Pfad absolut auf `.sock`, ohne `..`/`//`, nicht unter `/etc/meridian` oder `/var/lib/meridian`, höchstens 8 Profile; Ungültiges verhindert den Start). Ohne Angabe gibt es keinen Host-Executor (Lauf endet mit der festen Notiz). Die Variable gehört schon zur Umgebungs-Allowlist der Shell-Worker-Kinder.
6. **systemd-Betrieb vervollständigt:** Bisher gab es nur Web und Planer, der Planer führt aber nichts aus; es fehlten die Worker. Jetzt `meridian-worker-http.service` (Netz, Schlüssel, kein Docker-/Host-Socket) und `meridian-worker-shell.service` (nur `AF_UNIX`, `IPAddressDeny=any`); der Planer läuft ohne Schlüssel (`InaccessiblePaths=/etc/meridian`, kein Netz). Der Installer legt `meridian-run` an und startet die Worker; Host-Shell-Jobs nur mit `MERIDIAN_ENABLE_SHELL=1`.

## Nicht abgenommen
Getestet sind Protokoll, Agent und Executor gegen einen echten Agenten auf einem Unix-Socket (Ausgabe, Exit-Code, Umgebung, Signale an die Gruppe, Verbindungsabbruch, Protokoll-Fuzz, Isolationsverweigerung als root, Leak-Test über ShellRunner). **Nicht** gelaufen sind die Units unter einem echten systemd (Benutzerwechsel, Sandbox-Direktiven, Socket-Aktivierung); `systemd-analyze verify` meldet nichts. Vor dem Einsatz einmal auf einem Testserver durchspielen.
